# Sign-in and presence

How a contributor with their own Ooga becomes a player on the Cloudflare-hosted island. Other visitors explore signed out. Everything here lives in `worker/` and `src/js/net.js`; the page served anywhere else (GitHub Pages, a file, `npm run serve`) finds no backend and behaves exactly as before.

New Oogatron contributors can receive a server-verified default character before
their file reaches a deployed bundle. Eligibility, merge-time generation and the
PR ownership check are described in [Contributor onboarding](contributor-onboarding.md).

## Arcade cabinets

The twelve available video cabinets use `arcade-cabinets-v1` in the room's welcome features. `src/js/arcade-cabinets.js` names each cabinet and its physical play spot; Rally remains out of order. Carnival machines, including multiplayer air hockey, keep their separate rules.

Before a signed-in player opens a cabinet, the page sends `{ t: "cabinet", op: "take", id, q }`, where `q` is a positive request sequence. The room requires a driven body in `arcade.hall`, admits one player per cabinet and one cabinet per player, and answers `{ t: "cabinet", id, q, ok, reason }`. It checks and assigns synchronously. A `cabinets` message broadcasts the occupied cabinet IDs, player IDs and existing display names, including on a new connection.

While reserved, the room keeps the player's body, hall zone and canonical standing pose; game-world movement cannot move that avatar. The page stays in the same voice group. The matching `{ t: "cabinet", op: "leave", id, q }` releases the cabinet. Disconnect, stale-socket cleanup, socket replacement and forced body release also free it. Socket attachments preserve reservations across room hibernation. A late acknowledgement after cancellation is released using its own sequence, so it cannot release a newer visit.

The page waits for acceptance, refuses live play on an older server without the feature, and returns to the arcade after losing the connection. Signed-out play is local and does not reserve a cabinet. Public game links enter through the corresponding arcade cabinet; debug scene fixtures can still open games directly. No game progress or new personal data is stored in the reservation.

## Signing in

1. The Contributing Oogas panel’s **Contributor sign-in** calls `BL.net.login()`, which navigates to `/auth/login?next=%2F`. Sign-in from any scene returns to the hub.
2. `/auth/login` (rate limited, 10 a minute per IP) makes 32 random bytes of `state`, stores `state.<next>` in a ten-minute `HttpOnly` cookie (`__Host-obl_oauth` on https), and redirects to GitHub's authorize page. No scopes are requested: the public profile is all we read.
3. GitHub sends the visitor to `/auth/callback?code=…&state=…`. The Worker checks `state` against the cookie in constant time and clears it, trades the code for an access token, reads `GET https://api.github.com/user`, and **discards the token**.
4. Before writing a player or session, the Worker requires an owned character: an existing bundled character matched by its owning GitHub login, or a verified Oogatron contributor eligible for a temporary character. A character alias cannot be claimed by a different GitHub account. Ineligible accounts return to the saved same-site destination with a contributor-only sign-in notice; no account or session is written. The eligible player row is upserted by GitHub's numeric id (a renamed login stays the same player if it still owns a character). A banned player gets 403.
5. A session is 32 random bytes; the browser gets it in `__Host-obl_session` (`HttpOnly; Secure; SameSite=Lax; Path=/`, 30 days) and D1 keeps only its SHA-256. The visitor lands on the hub at `/`, where their own Ooga is selected awake beside the banana pile regardless of activity. Sign-in does not save the old scene or camera. Already signed-in visitors can still open direct scene and hub-place links, and ordinary interior exits retain their return locations.

## Remembered local character

After `/api/me` confirms a successful login, the page saves only its validated GitHub username in `ooga-last-github` (`Path=/; Max-Age=31536000; SameSite=Lax`, plus `Secure` on HTTPS; no Domain). It survives sign-out. The cookie is readable by the page and is only a preference; the Worker never uses it to authenticate or authorize a request.

Before normal scene construction, a signed-out visitor gets the remembered character if locally available, or a local default likeness for an unbundled remembered username. With no valid cookie they get **Ooga**. Local entries are excluded from shared NPC frames and never registered as GitHub-owned characters. An online owner's reservation still wins. `ownCharacter`, room joins and voice authorization continue to use the authenticated account only. `ownAmong` locks game selection to the authenticated or assigned local Ooga. Explicit debug fixtures keep their chosen cast and arrival.

## Being signed in

- `GET /api/me` answers `{ "player": null, "character": null, "donations": false }` or `{ "player": { id, login, display, look, createdAt }, "character": { handle, joined, lastCommit }, "donations": false }`, always 200, so a signed-out page logs nothing. `avatar_url` stays server-side while the content policy blocks GitHub images. `donations` is true once the Worker has its bananapayserver binding (`DONATIONS`): the page then takes real donations through its own address (`donations.useOrigin`), and until then stays simulated.
- Session reads recheck character eligibility for account, room, voice and signed-in donation attribution. Old guest cookies no longer identify a signed-in player. Bundled owners do not depend on Oogatron availability; an unbundled owner must still be verified by the bounded cached lookup. A refresh failure retains previously verified rows only until the original snapshot is 24 hours old. Unknown accounts remain denied, and a successful refresh replaces the rows immediately.
- The session is touched at most once every ten minutes, so reading it is not a write per request.
- `PATCH /api/me` with `{ "display": "…" }` sets the in-game name: the character set of `donations.sanitize`, 3–24 characters.
- A cron at 04:00 UTC deletes expired sessions; they are refused on read before that anyway.

## Signing out and leaving

- **Sign out** posts `/auth/logout`, which deletes that session row and clears the cookie. `/auth/logout?all=1` ends every session of the player.
- `DELETE /api/me` deletes the player, every session and their attributed high scores. Unattributed machine bests remain.
- These two removal paths accept a valid historical session even if its account no longer qualifies to sign in. The signed-out account controls does not show those historical sessions. With the island open, `fetch("/api/me", { method: "DELETE" })` in the browser console removes the retained account and all its sessions; `fetch("/auth/logout", { method: "POST" })` clears only this session. Check for a 204 response. They grant no other access. Expired sessions cannot authorize removal; contact the maintainer to remove the retained player record.
- Every state-changing request must carry the site's own `Origin` (or `Sec-Fetch-Site: same-origin`); anything else is 403.

## What is stored

For a signed-in player: GitHub id, login, avatar URL, the chosen display name, sign-in and last-seen times, and for each session its token hash, times and the first 120 characters of the user agent. Completed games can also set public high scores: Cloud Hopper's top 1,024 times carry GitHub usernames; arcade machine bests carry only permanent machine IDs. Attributed records retain the stable GitHub ID privately so a login rename follows its account and deleting the account removes its records. See [Shared game high scores](highscores.md). Nothing is uploaded from signed-out games or old local saves. No GitHub token is ever stored. The room also keeps the shared EntropyLab chalkboard's marks (see The EntropyLab chalkboard): what is drawn and written on it, with no names or ids.

## Presence

A signed-in visitor holds one WebSocket to `/room` for the page life. The Worker checks the site `Origin` and the session, strips any client `x-player-*` headers, sets its own (`id`, `login`, `display`) and hands the upgrade to the Durable Object `Room` named `island` (`worker/src/room.js`); the room trusts only those headers.

Frames the room cannot read close with 4400, as does any frame over 256 characters except a chat line; out-of-bounds poses, unknown types and unusable chat lines are ignored. The pure rules are in `worker/src/protocol.js` with their checks in `worker/test/`.

Gorilla locomotion `g` is six finite numbers: `[flags, speed, climbStride, climbDirection, climbSide, swim]`. The flag bits are airborne (1), biped (2), climbing (4), running (8), lab (16), office (32) and asleep (64); flags must be an integer 0–127. The remaining values are clamped to ±20, ±1,000,000, ±1, ±1 and 0–1 respectively. While asleep, `climbDirection` carries the resting pose (-1 left, 0 back, 1 right), and the remote rig suppresses movement and other locomotion. Only a gorilla body retains them. Changing body clears locomotion and resets health; the page invalidates its pose cache and reports the new actor even at identical coordinates. Welcome/join records include `g`, and room attachments preserve it through hibernation. This adds no idle timer or change to the five-number position stride.

An Ooga's jetpack `j` is an integer 0–7, for drawing only: 1 while worn, plus its flame's power (0–3) times 2 (`crew.jetFlags`), which other pages show on that Ooga with the same flicker (`remote-players.js`). The page sends it with a pose only when it changes, and a pose without it means none. Only an Ooga keeps one: a gorilla's is dropped, and a body change clears it. Welcome/join records and room attachments carry it as they do `g`, and each snapshot's `js` lists every non-zero one.

**Weapons.** An Ooga's weapon `w` is an integer 0–255, for drawing only (`crew.weaponFlags`): bits 0–1 the weapon in hand (1 the club, 2 the gun), bit 2 aiming, and bits 3–7 the rounds in the magazine (0–31; unlimited sends a full 30). It travels exactly as `j` does: with a pose only on a change, an Ooga's alone, cleared by a body change, kept in records and attachments, listed in each snapshot's `ws`. Other pages show the gun in place of that Ooga's club while it is out, raised while aiming, with a magazine banana for every three rounds (`remote-players.js`). Each banana the driven Ooga fires sends one `shot`: muzzle and landing point, each inside the room's bounds and at most 120 m apart; each club swing or gun bash sends one `swing`. The room relays them at once, no more than 12 shots a second with a burst of 6 and 4 swings a second with a burst of 4 for each player, keeps nothing, and takes neither from a gorilla body or a page with none. The pages replay a shot through the crew's own `showShot`, which draws the banana's flight and hits nothing, and a swing as a swing of the right arm. Damage stays local: nothing here is combat. Remote Oogas use the crew's same third-person equipment kernel for character-specific grips, carry, slings, recoil, swings and reloads. Local camera-only offsets stay local.


**Hammock presentation (#461).** The same pose may carry `r: 0` (explicitly standing) or six bounded integers `[seat, phase, progress, qx, qy, qz]`. The one seat is 0, phase is entry/rest/exit (1/2/3), progress is 0–255, and quaternion xyz is rounded at 1/1000 with a nonnegative implied w. Entry/exit use the existing world-position fields; settled rest uses a canonical seat so sway sends no traffic. Welcome/join and socket attachments retain `r`; snapshot `rs` rows contain `[id, ...r]` or `[id, 0]`. Legacy omission keeps the existing position inference. Ownership comes only from the shared equipment descriptor. No new socket, event history, idle timer, projectile state or inventory mutation is added; the combined bounded pose stays within 256 bytes.

The hammock moves the actual primary, rifle and owned jetpack model to a fixed ground holder for the seat's lifetime. Getting up restores their authored parents/transforms before the shared pose resumes; body removal and both retained and released scene exits remove the holder immediately. An owned but unworn jetpack uses the same existing geometry, without equipping it or creating a pickup. The room's present disconnect lifecycle still releases a closed socket immediately. The retained-occupant/grace/recovery policy in #377 remains a separate dependency: a retained remote record keeps this visual state, with no independent grace timer here. Two authenticated-client checks, transitions and reconnects must be repeated when that lifecycle lands.

**Live-player presentation (#464).** Optional `pose.v` adds 17 bounded integers to the existing pose, never another socket or message type: head pitch, weapon aim pitch/yaw (centiradians), flags, recoil remaining, reload cycle, handoff remaining, magazine-swap remaining, melee remaining, held wind-up elapsed, charge (0–100), ready-hold remaining, axe idle time, bash remaining and twirl remaining (durations in milliseconds), then two spare-magazine counts (0 absent, otherwise rounds + 1). Flags are primary/AK/jetpack ownership (1/2/4), reloading (8), spare loading (16), held wind-up (32), quick cut (64), reverse cut (128), handoff (bits 8–9: none/back-to-rifle/to-spare/between-spares) and twirl hand (1024), the loading magazine index (2048) and the swapping magazine index (4096). Ownership describes presentation only; it never changes inventory or ammunition. The room stamps receipt as `va`, carries `v/va` in welcome/join and socket attachments, and snapshots carry `[id, va, ...v]` rows in `vs`. Missing presentation clears prior state; only an owned Ooga retains it, and body/cabinet release clears it.

A changed look or action sample earns a normal pose at the existing 10 Hz limit; an unchanged idle look adds no messages. Held wind-ups and reloads have a 300 ms pose heartbeat. Remote timers advance from the room sample's age; a reload or held action without a fresh sample ends visually after 500 ms, never completing ammunition or damage. Reconnect restores cached ownership/look with transient actions cleared and spare counts retained, then reconciles the next current sample. Existing shot/swing events remain the sole effect events; a new presentation sample supplies swing phase rather than replaying the event. Scene callbacks still park weapons where disallowed, including the poker and Timechain rooms.

The extension adds at most 88 JSON characters for `v` at its declared bounds (the full Ooga pose remains below 256), plus the id and receipt time per snapshot row. It adds no idle timer, database write, projectile stream or NPC snapshot field. A remote allocates its small weapon/quaternion state once when its rig is built and reuses it. Build/syntax checks do not establish two-client visual fidelity: carry/primary variants, reload interruption, continuous look, first-person differences and reconnect remain maintainer play-test checks unless an explicit runtime test run is requested.

Old open pages still understand Ooga poses but interpret `gorilla:<handle>` as an unknown Ooga handle. They can show a hashed Ooga alongside their still-active local gorilla, rather than the remote companion. Refresh all participating pages together for multiplayer companion play; the room does not negotiate client versions. The extension carries locomotion, not attacks, captive Oogas, throws or authoritative combat damage.

### Zones

Where a signed-in player is decides whom they hear and see. A zone is `<group>` or `<group>.<place>`: voice is shared within a group, and players are shown only to others in the same zone, since a hall has coordinates of its own.

The exception is **the main world**: every zone the island scene reports (`outside`, `between`, `rainforest`, `rainforest-under`, `sphere`, `bifrost`, `hq` and `hq-basement`; `WORLD` in `voice-blend.js`), all in that scene's coordinates. Everyone in it is shown to everyone else in it, whichever of those they stand in, and what they send of themselves (shots, swings, reactions) reaches all of it (`seenTogether`). Its voice goes by height rather than zone (see Voice).

The hub works the zone out every frame from the driven Ooga or gorilla (`zoneOf` in `scene-hub.js`) and reports a new one once it has held for a quarter second, so a bridge's foot does not flicker in the panels. Every other scene declares its own (`voiceZone` on the scene object, set by the director on entry); DSB Land reports its venues as it goes. The games keep `scene-<id>`, with no actor driven and so no voice, and are listed as Ooga Arcade, only Ghost Hunter's Arena apart. The banner's line under its title reads the visitor's zone by the same names (`line` in `zone-map.js`, drawn by the director wherever a section carries `data-zone-line`), the main island keeping "The Island of Caves".

Each remote visitor driving an Ooga in the same zone, or anywhere in the main world for a visitor on the island, appears as that Ooga (`src/js/remote-players.js`, in the island and every scene with Oogas to drive), eased toward the room's poses, with their name above their head and, while they are in voice, a speaker below it (green while speaking, red with a cross when they muted their microphone). Ordinary scenes show no health bars; games can opt into a bar from the room's `hp`. The local crew's copy of the same Ooga steps `away` while someone else drives it and comes back when they let go, so no Ooga stands twice (the Arcade hides its crowd's copy the same way); the NPC crew keeps working and walks round remote bodies. The island instead keeps that copy on its own track as a ghost (see NPC ghost tracks below).

**NPC ghost tracks (the island).** While a signed-in player drives an Ooga or its gorilla, the driven body is separate from that character's roster NPC, which stays the same object with its own AI, route, fire seat, bed and continuous activity: chilling in its own place by the fire, clanking along its work path, or asleep in its bed. Every page draws that NPC as a Cloud Hopper replay ghost (`npc-ghosts.js`: cyan, glassy, shadowless), and its harmless work rounds fly in the same colour (presentation only: no hits, reactions or prop effects, and the passive NPC policy is unchanged). Under the cursor a ghost Ooga or gorilla shows its name and the NPC's own activity dot (working, chilling or sleeping; a gorilla's by its Ooga), never the online dot, which belongs to the driver's live body, as long as the ghost itself is in sight and no live player stands in front of it; the crosshair never counts a ghost as a target, while a live player in plain sight under it turns its dot friendly green. Gorilla companions are not in those frames: every page runs its own companions from the host's Ooga states and the plan and hit events the frame carries, as before, so a ghost companion's pose can differ between pages. A single authoritative companion host is outside this change. When the room reports the driver gone (a release, a body change, a disconnect or a sign-out) the remote body goes as before and the NPC turns solid where its track has it. There is no new timer, freeze or hold, and signed-out play is unchanged.

Only a contributor's character is drawn as a ghost, whether its driver is signed in or out: a signed-out visitor driving their remembered contributor's Ooga sees its ghost on their own page too. A guest's local likeness (the default **Ooga**, or a remembered unbundled login's, `contributors.addLocal`) belongs to no contributor: crew.js marks it `avatar`, so it has no NPC copy on the island and no ghost. The visitor's driven body is the only one there is; when nobody drives it, it is away. The roster record decides this, never the account.

The body owns the page's persistent `world` weapons, health and magazine, carried across scenes as before; roster NPCs keep their AI inventory in the crew's own maps. Switching between Ooga and gorilla, a revoked claim and leaving the scene dispose the body and leave the NPC where its track has it. The visitor always drives one: Escape never lets go. A sign-out keeps the Ooga that is still theirs to drive, and a room lost or regained (a disconnect, a hidden tab's pause, a kick) changes nothing on the page; the room hears the body again once it is live. When an account change makes the driven Ooga no longer theirs, the hub lets it go and hands them the one they may drive now (`claimOwnOoga`), and switching accounts claims the new account's own. The NPC sync frame is format 3, which keeps driven identities' NPCs in the frame. A format-3 page whose elected host sends another format holds every NPC where it stands, runs no crew AI of its own and says once that the host is on another version; it follows again when a matching frame arrives or the room elects another host. Older (format-2) pages can't do this: one following a format-3 host still drops its frames and runs its own crew, and a format-2 host sends driven Oogas' NPCs not at all, so the island looks consistent only once every page has reloaded. The EntropyLab scene, DSB Land and the Arcade keep their own behaviour.

The Ooga Boogas panel shows every signed-in player online, in every scene: the row of their own Ooga and the row of the Ooga they drive get the green dot, and online rows lead the list. One who disconnects drops back to their activity's place.

### Who drives which Ooga

Every Ooga belongs to a contributor, and ownership keys on the GitHub login alone: a character's `github`, or its handle when it has none (`bc1gui` is owned by `ottoz0r`; a different GitHub account that happens to be called `bc1gui` owns nothing).

- A signed-in contributor drives **only their own** Ooga in multiplayer. The hub hands it to them awake on arrival (`claimOwnOoga`), whatever its activity: a separate body standing where their NPC is (the nearest clear spot beside its bed or seat), the NPC keeping that activity, or beside the banana pile while the NPC is away and has no place on the island. This happens once a visit, unless they already drive another; returning actors keep their interior's exit. A fresh signed-in hub arrival takes priority over a `view=` viewpoint; a link to a hub place (`/mempool`, `/sphere`, or the keypad a `/sphere-N` link sends out to) still arrives there. Every scene arrives with the visitor's Ooga: the one carried from the last scene, else `character=`, else their own or assigned one (`BL.net.preferredCharacter()`), always gated by `net.mayDrive`. There is no free-roaming camera and Escape never lets go. If an account change makes the driven Ooga no longer theirs, the hub hands them their own again, and the Factory, hangar, ₿IFRÖST, Arcade and poker room toast and leave toward the island.
- Every signed-in player has an owned character. There is no signed-in borrowing path; a missing client character mapping refuses selection until the owned character is available.
- Signed-out visitors control only their remembered Ooga, or the default **Ooga** when no login has been remembered, and its companion. This also locks game pickers and static-hosted visits to their assigned character. They have no room socket or remote roster, so local control cannot check who is online elsewhere, publish a multiplayer claim or show a green signed-in marker. Logout keeps the last verified character as a local preference.
- A signed-in contributor may also claim **their own gorilla**, including a server-vouched temporary contributor. `net.mayDriveGorilla` and the room both check the companion's owner. T cycles the owned pair on the hub; G keeps its existing weapon/grab meaning. Companions remain in the hub's playable areas, rather than separate scene interiors. Signed-out/static gorilla play is local, with no room publication.

Hub world selection and T validate the target before releasing the current actor. A refused or unavailable actor leaves the current control and camera intact and shows the reason. Selecting the current actor does nothing. Switching between controlled actors preserves carry/combat and the view family. Sleeping actors stay asleep until Space or the wake button is pressed.

Pile arrivals leave room for both displayed remote bodies and the latest room poses, including a snapshot received before the remote pool updates. Joining does not reset the shared crew: the elected host keeps its simulation, and a follower's cached NPC frame cannot move an Ooga driven locally or by another player.

If an unanswered account lookup succeeds on Retry while the Sphere's keypad holds the visitor's own Ooga, that interaction keeps its position, view, and selected room. Account recovery does not restart arrival at the pile.

The room rejects accounts without an owned body before accepting their socket. Historical guest attachments are evicted when the room wakes, receives their next message, or runs its existing stale sweep, so they cannot keep chat, voice or NPC-host access. This adds no timer or background contributor lookup; an already accepted temporary contributor retains its verified attachment until reconnect.

The page enforces ownership (`net.mayDrive`, checked by `pilot.possess` through the scene's `mayPossess`). The room independently enforces it (`claimRefusal` in `worker/src/protocol.js`, over the cast `npm run build:site` writes to `worker/src/characters.gen.json`), so a tampered page cannot take another contributor's Ooga; a refused claim answers `release { name, reason }` and is never shown to anyone. Normal static-hosted visits enforce the same assigned-character restriction. Explicit debug pages (`?debug=1`) prepare no local identity and keep the bundled cast for local scene testing; signed in, they too drive only their own pair.

A second tab of the same account takes over: the first is kicked with `replaced`, stops reconnecting, and its Contributing Oogas panel offers **Play here**. Every deploy drops every socket; pages reconnect on their own with backoff (0.5 s × 1.7, up to 15 s). A tab hidden for five minutes leaves the room (voice stops) and rejoins when it is shown again.

**What keeps the room cheap.** The room is a Durable Object, billed for the time it is awake and for the messages it receives, and it sleeps (hibernates) only when no timer is pending and nothing arrives for a few seconds. So nothing in it runs on its own: a pose schedules one snapshot, voice lists go out when who hears whom can change (a join or leave, a body or zone, a voice session), `vstate` goes out when a microphone goes live or off or is muted, `hp` when a driven Ooga's health moves, and the stale sweep is an alarm once a minute. Voice the room closes at the SFU (a player who left, changed zone or lost a Studio permission) and the SFU has not confirmed retries from an alarm at most a minute apart, even after the last player has left, until it succeeds or an hour has passed (`CLEANUP_MS`); with no SFU configured, nothing wakes for it. Pings are answered without waking it. The NPC host sends only while another page follows it (`followers`), four frames a second, and skips a frame when no Ooga changed and nothing happened (at most 2 s).

## The crew in step

Signed-in players on the island see the same Oogas doing the same things (`src/js/npc-sync.js`). Without it every page runs its own crew, and random choices and frame timing drift each page apart within seconds.

- **One page runs the crew.** The room elects a host: the sitting host while it still shows the island, otherwise the page longest in the room among those that do (the hub scene, in a visible tab; `{ t: "hub", on }` reports it). The room tells everyone with `host { id, followers }` and hands over when the host leaves the hub, hides its tab or closes; a page that comes back does not take hosting back, but follows and catches up from the host's frames.
- **The host streams what shows.** While at least one other page follows it, four times a second it sends one binary frame with every Ooga nobody drives: a header (format, a signature of the ordered crew names and work-site identities, a record count, the event bytes), one record of floats per Ooga, then the events since the last frame as JSON. A frame identical to the last one sent, with no events, is skipped for up to 2 s. A record carries the body (root position, rotation, quaternion, scale and visibility; legs, arms, head with its eyes open or closed, torso), the gear (which holder the club and rifle hang from, hand, back sling or bed, and their pose; the rifle's bananas; the flash; the snack; the bed's weapons), status (stun birds, fire embers and scorch, colourway, a built-in jetpack's flame) and the work the gorillas follow (state, phase, the cave worked, the cave planned). Events are what happens once: speech, sleep marks, landing dust and jetpack sparks, every banana shot's flight, and the gorillas' plan and hit. About 6 KB a frame for a dozen Oogas. The room takes frames only from the host (185 KiB and 20 a second at most), relays them to every other page on the island, and keeps the latest for anyone arriving.
- **Followers pose puppets and replay events.** On every other signed-in page those Oogas are puppets (`cave.puppet`): `crew.update` skips their AI, and npc-sync plays them back after the crew's update, a send interval and 0.1 s behind the frames' arrival on that page, on the straight line between the two frames either side, so frames arriving evenly play a steady walk at a steady pace (arrival jitter can still vary it, and a straight line between frames far apart can cut a corner the host walked round); it holds on the newest frame rather than guess past it, and places one at once when it jumps far or changes status (into a bed, back from a fall). A frame's events replay when playback reaches it. Gear changing holder is moved there and the mirror and outlines refreshed. Events replay through the page's own effects; shots fly as visual-only rounds (`crew.showShot`: no hits, no mirror crossing), and the gorillas get the host's plans and hits, so they travel and react in step without a stream of their own. An Ooga someone drives is never a puppet: its driver's page runs it and the others show it as a remote player.
- **Measured** (at the earlier ten frames a second): two and three pages on one machine kept every Ooga within 0.4 of the host's (0.05 on average), and every undriven Ooga's gear, eyes, colourway and work state identical in samples 6 s apart; a follower replayed the host's sleep marks, 71 shots with their 70 gorilla hits, the gorillas' plans and a poked Ooga's speech. A host closing handed over within seconds and a new page followed the new host.
- Visitors who are not signed in have no room and keep their own crew. No database is involved: the latest frame lives in the room's memory.

HALLOWEEN: the arcade's ghost hunt has a host of its own, elected among the visible pages in its arena (zone `ghost-arena`, hunting or not; an older page's `arcade.arena` or `arcade-hunt`); pages in the arena's hallway (zones `arcade.haunt` and `ghost-arena.haunt`) follow it too, and a page that steps across the hallway's midpoint is not handed the kept frame again. Each follower page plays the hunt's music and every sound effect at the arena's equal-power share of where its driven Ooga stands along the hallway (sin(πt/2) of the way from the Arcade end to the gate, full in the arena, none in the hall; `hearing` in `scene-arcade.js`, `level` in `ghost-audio.js`), whether or not it joined the hunt. Every cue the snapshots drive plays on each such page; the cues that start on one page are carried too: an arena player's rifle shot, which the room relays from the arena to the arena and both hallway halves (a shot from the hallway stays in its zone), sounds once on each page that hears it, and a hunter's hurt sounds for a page not in the hunt from the snapshot's health (a hunter hears only their own, and their own hits). A page catching up on a hunt after a gap of more than 1.5 s (a late join, or back from the hall) holds the cues of the frame that applies it, so nothing that happened meanwhile sounds at once. Where it hears nothing, no cue is scheduled, no audio context is opened for it and the playlist stops; a track that finishes decoding after the hunt is disposed starts nothing. While a hunt runs, that host sends the whole hunt as `ghost-sim.js` snapshots it (state, round, its random draws, every ghost, the boss, drops and players, timers on the hunt's own clock) four times a second as a binary frame led by `GHST`, so a follower in the arena or its hallway draws it and a new host picks it up where the old one stopped. Followers send their herald click, their ready, their leaving and their hits as `ghost` messages, relayed to the host alone; the host judges every touch, beam and pickup from the players' reported poses, and each page applies its own Ooga's damage from the snapshots. Only pages in the arena or its hallway hear the hunt: a spectator in the hallway watches it through the fence, and only pages in the arena are shown its lobby or may report to its host.

The banana pile level, donations, crates and what shots do to the world (the mirror, breakables) stay each page's own. The gorillas' own motion runs on each page from the same plans and hits, so it stays close rather than exact.

Everyone in the room hears the same fire at the pile at the same moment (`src/js/pile-audio.js`). ## Voice

Signed-in players can talk (`src/js/voice.js`, `worker/src/room.js`, `worker/src/sfu.js`), over a Cloudflare Realtime SFU app per Worker (`REALTIME_APP_ID` in `wrangler.<env>.jsonc`, `REALTIME_SECRET` a Worker secret).

- **Join voice** in the account row of Contributing Oogas, Online Oogas or Ooga Chat asks for the microphone, then becomes **Mute** / **Unmute**, beside **Leave voice**, which hangs up and releases the microphone while the visitor stays signed in and in the room; a failure says why on the button.
- **M** toggles microphone mute while voice is enabled or joining, across scenes, panels and dialogs. Input fields and editable content keep M for typing; modified browser shortcuts are untouched. This changes mute state without requesting a microphone, including for listen-only visitors. With voice off, M controls environment sounds outside focused UI.
- **Who hears whom: the same zone group, or in the main world the same level** (see Zones). Players driving an Ooga or gorilla hear each other while they are in the same group, and nobody outside it; the main world goes by height, below. Within a group every voice plays at the same volume, however far apart the actors stand, unless the listener changes that player's volume or turns their own hearing range down (#380): the Online Oogas panel's Advanced settings contains Hearing range and Read joins aloud. The range is 1–60 m in 1 m steps, plus no limit (the default), kept in this browser. A voice plays at full inside the range and is silent at or beyond it, measured between the two players in the place they both stand in. Slider changes apply immediately; movement updates the cutoff on the existing 150 ms meter read, without a distance fade or gain ramp on desktop or iOS. Closing Advanced settings leaves the choices active; a voice in another place of the group (the Factory's hall and hangar each have coordinates of their own) counts as past the range. **The main world goes by height, not group** (#392; `voice-blend.js`, `levelOf` in `scene-hub.js`). Everything on or over the island's plane (reaching a metre under it, for the land's lowest dips and the bridges' sag) is one place, the surface: the island with its cave entrances, the bridges, the air off the edge, the top of the Sphere and its outside, the ₿IFRÖST isle and the rainforest's top level. So with no hearing limit a player there hears everyone else there. Below the plane the levels fade into each other by height, on an equal-power curve (cos(πt/2) and sin(πt/2), about 0.707 each halfway): the surface into HQ's level down to HQ's floor, then HQ's into its basement's down to the basement's floor, the same over the island or out in the air off its edge on a jetpack. Inside HQ's rock the height decides only on its ramps and below its floor; its rooms are HQ's level, furniture and jumps included. The rainforest's top fades into its tunnels and chamber inside its rock, from below its lowest terrace to the chamber's floor, never the lake's water over the chamber; under the islet in the open air the island's own levels go on. Each level hears only itself at its own height. A level is not a zone: a player's zone (the land listed in the panels) never changes what they hear, and walking from one zone of the main world to another drops and re-pulls no voice. Halls and portals stay their own voice groups, the ₿IFRÖST chamber apart from its isle and the Factory's and Arcade's halls apart from their entrances. Ooga Arcade's haunted hallway blends between the Arcade and Ghost Hunter's Arena (#422), by where the driven Ooga stands along it (never the camera): each half reports its own land's zone with the crossing toward the other land (`arcade` or `ghost-arena`, each the whole group, `voice-blend.js` `place`), both at about 0.707 at the midpoint, where the zone flips and the room and the page turn the crossing round rather than drop it, so no voice is closed and pulled again there (the room sends the walker its unchanged list once, which the page applies as no change, and other pages turn the walker's crossing round from the `zone` itself, before its `blend` follows). The arena is one region with or without a hunt, so the hallway's arena end hears its hunters. The hall, the hallway and the arena share the arcade scene's coordinates, so the hearing range is measured between them. The page reports how far along (`blend`), the room lets a player hear exactly the players they share a place with, and the page sets each voice's level: the same share both ways, full between two players side by side, times the hearing range, which in the main world measures between any two players in it. The hearing range only turns down this page's playback: the room, the microphone, what others hear and what is pulled from the SFU stay as they are, so it saves no bandwidth, and a mute still wins. Each voice plays through a Web Audio gain in the context the Join click makes, with its element kept muted. The gain carries the individual volume, the Studio's voice level and the local mute along with hearing range and crossing gain. Boost is limited to 2× (+6 dB), with peak compression for boosted voices; normal levels bypass compression. Browsers without Web Audio retain element playback and offer quieting through 100% only. If Safari suspends that context (a call, another app), the next tap or key wakes it. A player in a game or nowhere (`none`) is out of voice, except the [air hockey pilot](air-hockey-pilot.md): its seated Ooga stays in `arcade.hall` throughout the lobby, match and results, with the existing hearing range and mute settings. Every scene with an actor to drive keeps the driving rules, reports the actor driven there every frame with its pose and health (`net.setBody`, `sendPose`, `setHealth`) and clears it in `leave`. On the island, an actor taken over where it already stands inside a cave counts as in that cave, not only one that walked in through the mouth.
- Each page opens two peer connections, one publishing its microphone (the browser offers, the SFU answers) and one receiving (the SFU offers, the browser answers). Every SFU call goes page → Worker (`POST /api/voice/{session,publish,live,pull,renegotiate,close,leave}`, same-site and signed in, 120 a minute) → room → SFU. Only the room holds the secret; a page never sees another player's session.
- A microphone is announced only after its publishing connection is up (`live`): pulling a publication before it connects fails. The room recomputes who hears whom whenever it can change, sends `voice { peers, gens }` when a list changes, and re-checks it on every `pull`, so a page cannot pull a voice it may not hear. The last list each player got is kept in its socket's attachment (`sent`), so a room that slept still sends a list that has just gone empty; it used to assume one had been sent, which left a page hearing a player who had gone, or deaf to one who came back. Each microphone that goes live gets a new count (`gens`), so a page re-pulls a player who published again rather than staying on their dead track. Each page applies one change at a time; a change that fails, or a pull that misses a wanted voice, is retried once on a fresh receive session before the button says voice is unavailable. The first publish gets a second try, and a connection that fails or stays dropped five seconds after it was up starts voice over on its own.
- **Alone, the microphone is off** (#181). The page's `voice` list is exactly whom it may hear, and since everyone in voice publishes, it is also everyone who could hear it: while that list is empty the page holds its microphone track off as a mute does (`stats.alone` in `voice.js`), still published so a newcomer is listed and pulls it, and turns it back on when the room lists someone. It is a client-side gate: the room is not told and needs no change, and a visitor's own mute stands. The note under the clock says "Alone · mic off".
- Sign-out and another tab taking over release the microphone; a reconnect (every deploy) rejoins voice on its own and keeps the visitor's mute, unless they left voice.
- **The roster shows it.** In the Ooga Boogas panel each signed-in player's row (their own Ooga, else the one they drive) carries a voice mark after the name: grey while in voice, green while speaking, red with a cross when they muted their microphone. The room's NPC host has a black dot. Speaking is measured on each page (an analyser on its own microphone and on every voice it receives), so it shows only for this visitor and the voices they hear; others show grey or red. A click on another player's mark mutes them for this visitor alone (a slash) and again unmutes them: saved with that player's volume by their stable GitHub numeric ID under the listener's account ID in this browser's localStorage (`oogaboogaland.voice-players.<listener-id>`), never sent anywhere. A different signed-in listener gets their own settings; a renamed player keeps theirs, and a new owner of an old login does not inherit them. The old unscoped mute list, including numeric speaker entries from #459, is left untouched and not imported because it has no reliable listener identity. Saved mute and volume apply before a newly received voice becomes audible, and changing volume never unmutes someone or crosses the room's audience, zone or hearing boundaries. Their voice is still received, only not played.

The place is reported by the page, as positions are; a tampered page could claim another place to listen there, but only as a signed-in player whose login the room knows.

## Ooga Chat

One conversation for every signed-in player on the island, in the sheet's last tab (`src/js/chat.js`, `worker/src/room.js`, the `CHAT_*` rules in `worker/src/protocol.js`).

- **Who sees it.** Like Online Oogas, the tab and panel are hidden while signed out, including in restored or detached layouts. **Contributor sign-in** is in the Contributing Oogas panel on desktop and mobile. Choosing the tab focuses the input on a mouse or trackpad, not on a touch screen, so a phone keyboard does not cover the log until asked for.
- **Names come from the session.** Every row shows the editable display name alongside the authenticated `@login`, so a display name does not stand in for identity. The chat panel edits the display name through the existing same-origin `PATCH /api/me` (3–24 supported characters); success updates the local Ooga’s overhead hover name and reconnects the room using fresh authenticated headers. Whatever identity a page puts in a chat frame is dropped. Existing rows keep the name used when sent.
- **Text.** `src/js/chat-policy.js` is the same policy on the page and Worker. Ordinary Unicode letters, punctuation, emoji (including joiners and variation selectors) and URL-looking text are retained. Only surrounding whitespace is trimmed; text is not normalized, stripped or truncated. Empty lines, malformed surrogate pairs, C0/C1 controls, line separators and bidi overrides/isolates are refused. Natural RTL text is allowed. The limit is 160 UTF-16 code units after trimming, not 160 graphemes (a banana emoji uses two units). An overlong draft stays editable; server refusal is nonfatal. Donation-note and display-name policies are unchanged. The existing 1,024-unit chat-frame bound remains. Received malformed or overlong lines are rejected instead of sliced.
- **Mixed versions.** The room advertises `chat-unicode-v1` in welcome.features. A new page connected to a server without that feature permits only the old ASCII set and explicitly explains why extended text is blocked, retaining the draft. The sender repeats this check even if the UI is bypassed. Every non-live transition clears the capability; each welcome re-establishes it. Older pages may still restrict outgoing text; they render new incoming text as textContent. Roll out the Worker and the matching page together; rollback/reconnect returns to the explicit compatibility gate. No account or donation protocol changes.
- **Security boundary.** Chat rows, authenticated names and announcements use textContent, never HTML. URL-looking content stays plain text: no auto-link, navigation, fetch, preview or javascript: action is added. The authenticated room names the speaker, bounds and rate-limits frames, and retains chat only in its in-memory ring. Chat text does not enter D1/SQL or the Tess prompt; this change adds neither route. Existing account/Tess database queries are parameterized with bind. Consequently no new AI prompt path needs an injection filter here. A future chat-to-AI feature would require its own untrusted-input boundary and review; these changes do not authorize one.
- **Rate.** Each authenticated account has a bucket of 3 lines refilled at 1 a second (`CHAT_BURST`, `CHAT_HZ`), retained across disconnects and tab replacement while the room remains awake; lines over it are refused with `chat-rejected { clientId, reason }` and the socket stays. The input keeps its draft until the room acknowledges its outgoing `clientId` with `chat-ack`, allows one pending send, and preserves edits made while waiting; a refusal asks the player to retry. A disconnect also keeps the draft.
  The bucket map holds at most 64 accounts (`CHAT_BUCKET_KEEP`). Joins and sends needing a bucket opportunistically remove fully replenished inactive entries; if the map is full, a new account is rate-refused until space is available, rather than evicting an account with outstanding debt. No cleanup timer or durable storage is added. Hibernation, restart or redeploy resets all buckets, so this is awake-room anti-spam hardening, not a durable account quota. The outer `/room` connection limiter still allows at most 20 connections per minute per account.
- **Retries.** The page retains a random outgoing `clientId` across a disconnect or rate refusal and reuses it when the same sanitized draft is sent again. Editing into a different message or sending an identical text after acknowledgement creates a new id. Acknowledgements and refusals only affect their matching pending id. The room remembers the newest 3,200 accepted `(authenticated player id, clientId)` pairs and SHA-256 text digests in memory across socket reconnects; a recognized retry is acknowledged without another broadcast or rate-limit token. Reusing an accepted id for different text is refused. Oldest entries expire at the cap; sleep/hibernation, restart or redeploy clears them, and reloading the page loses its retry id. This prevents recognized retries, not durable exactly-once delivery after reset or eviction.
- **Ephemeral retention.** The room keeps the last 100 lines (`CHAT_KEEP`) in memory only, never in storage or D1, and sends them to each joiner. The room sleeps when nothing has happened for a short while, even with players connected (hibernation), and waking clears that memory, so a quiet island's history is soon gone. A page keeps every line it has seen up to 100, merged by id with what a rejoin brings, until it reloads or explicitly signs out. Successful sign-out clears this page’s transcript, draft and pending retry; temporary disconnects preserve them. The retry map keeps digests rather than older full message text; digests are not encrypted history and may be guessed for predictable messages. Other connected pages keep their own transcript until their reload or sign-out. Line ids follow the room's clock, so a woken room does not reuse one.
- **Delivery and input.** One bounded 10-second timer runs only for an outgoing line awaiting a receipt. Timeout reports uncertain delivery and enables a retry with the same id; it does not claim failure or automatically resend. A matching late receipt can resolve that send, but cannot clear a later edited draft (including edits back to identical text). The transcript is not a live region: only new visible live lines and status transitions are announced, never reconnect history or old rows drawn on opening. Enter sends and Escape leaves the input outside IME composition; keyboard focus stays in the sheet, and its inputs do not drive the game.
- **Unread.** A line from someone else that the page had not had, heard while the visitor is not attending the visible Ooga Chat panel (`sheet.attending`, as for Players above), counts as unread until they explicitly open the Ooga Chat tab. Its count appears on the tab when the panel is closed and in the notification bell when open. Inspecting the bell, focusing or scrolling inside the panel, and layout changes do not acknowledge it; opening another tab clears only that other tab. The lines handed over on arrival never count; on a rejoin (a reconnect, a tab back from the background) only lines newer than any the page had, by id, which follows the room's clock. Signing out clears the count.
- **Cost.** No frame work: a line heard while the tab is not showing only joins a capped list, drawn in one batch when it shows. The log follows new lines only while scrolled to its foot, including on reconnect; a reader keeps the same visible line when history merges. There are no idle chat timers; the pending receipt timer is cleared on resolution, disconnect or sign-out.

## Reactions

An X Spaces style card of ten emoji and a pinned raised hand, under Online Oogas' list and under Ooga Chat's input (`src/js/reactions.js`, the shared `src/js/reaction-policy.js` over the baked `src/js/emoji-data.js`, `worker/src/room.js`, the `REACT_*` rules in `worker/src/protocol.js`).

- **Who sees it.** Signed in only, in a room whose welcome lists `react-v1`; an older Worker leaves the card hidden. A reaction shows over the sender's driven Ooga or gorilla for about 2.6 seconds, on every page in the sender's zone that shows that body (`remote-players.js`), and over the visitor's own head at once. The raised hand stays over the body, and beside the player's name in Online Oogas, until it is lowered; it goes to every page in the room and survives the room's hibernation in the player's attachment. A reconnect sends it again; signing out lowers it.
- **What it can be.** One emoji from the baked list (Emoji 15.1's `emoji-test.txt`, every fully-qualified emoji up to Emoji 15.0), plain or in one of its five skin tones, never text. The page and the room check it with the same policy; the room drops anything else without a word. The hand carries a skin tone 0 to 5.
- **Choosing them.** A long press on any of the ten (a right click, the context-menu key or Shift+F10 on a keyboard) opens a picker floating in the middle of the screen: every emoji by group, a search by name, a skin tone (for every emoji that takes one, the hand included) and a heart colour (any heart in a slot shows and goes out in it, red by default). The choice replaces that slot, swapping with a slot that already held it. The ten, the tone and the heart colour stay in this browser's localStorage (`ooga-reactions`, `ooga-reactions-tone`, `ooga-reactions-heart`); Reset puts the defaults back.
- **Rate and cost.** One bucket a record for reactions and the hand together, 3 a second bursting to 6 (`REACT_HZ`, `REACT_BURST`). The page (`net.js`) spends a mirror of it for both, a little short of the room's (2.5 a second, 5 at once) since frames can arrive bunched, so a tap the room would drop shows nothing locally either. A hand change the room still refuses is answered to its sender alone with the hand the room holds, and the page puts it back, so no page ever shows a hand nobody else sees. Nothing is stored, logged or timed by the room; the page draws reactions on the overlay with no frame allocation and builds the picker's grid once a page, on its first opening.

## Private conversations

Two signed-in players can talk privately, one conversation at a time (#188). The messages are sealed with a one-time pad the two swapped outside Ooga; the room passes them on and cannot read them. The design follows the issue's text-chat version; voice is not covered. It was reworked after an AI security review of #436 and a review by MrHodlX on it; the issue's independent review is still to come.

- **Starting.** A lock on another signed-in player's row in Online Oogas invites them. The invite shows in Ooga Chat's panel, which gains a switch between the island's chat and the private one (its own blue tint and lock, so a line meant for one person is never typed into the island's). They accept, decline or block; clicking the lock of someone who asked accepts. Two who invite each other are talking.
- **The lock.** Each row's lock says where the visitor stands with that player (`privateChat.lock` in `src/js/private-chat.js`): open and grey with nothing between them; amber (pulsing gently, held steady under reduced motion) while an invite either way waits, the room opens the conversation, or the pad is not yet loaded and acknowledged; shut and blue once the line is sealed, after this side's hello was acked. The switch's and the private view's title lock follow the same colours. One conversation at a time: while the visitor asks or talks with someone, every other row's lock is dim, and clicking it shows the private view with what to cancel or end first. An invite that arrives meanwhile waits, and shows once the current one ends, unless its sender takes it back.
- **Ending.** Cancel takes back an invite; End ends a conversation, before or after the pad, for both sides. The room's late word for a step the visitor already undid never brings it back: its `inviting` only confirms, and an `open` for an invite or accept cancelled on its way is ended at once. The other side leaving, signing out or reconnecting ends it with a `left` reason the page tells apart from a no, and an accept that arrives after the inviter left is refused as `offline`. This page losing the room ends it with a note that stays readable until the room is back (another tab taking over says so); signing out forgets the conversation, its invites and its notes.
- **The pad.** Each side loads the same pad file, or one of them makes it here (256 KB, 1 MB or 16 MB of `crypto.getRandomValues`), downloads it and hands the other a copy outside Ooga, in person or over a channel they trust. The file names the two GitHub logins it was made for, so a pad for anyone else is refused by name. The page holds the pad in memory only and zeroes it when the conversation ends, after closing the session so nothing still in flight seals or reads on zeros. Ooga never uploads or stores it. The file itself keeps every byte ever used, so whoever later has it and the frames the room relayed can read the whole conversation; the panel says to keep it safe and delete every copy when the conversation is over.
- **Fingerprint.** Both see 20 hex digits of the SHA-256 of the whole file, to compare outside Ooga. The two pages also compare the digest themselves before either may speak, so a different file, or a copy cut short, never opens the line.
- **Sealing.** A pad file is a header (magic, a 16-byte pad id, the two logins) and two equal halves, one for each sender, so the two directions never share a byte. Each half is a region of 32-byte key slots and a stream region, so no byte is ever both a key and pad for text. Each frame takes the next key slot for an HMAC-SHA256 tag (WebCrypto), and a line takes the next stream bytes for its text, which begins with a 4-byte line number: the stream offset it was first sealed at. The tag covers the version, pad id, direction, slot, stream offset, length and body, so a changed, cut or reflected frame, or one sealed with another pad, is dropped without showing any of it. Knowing a line's text tells the room nothing about any key, so it can't forge a line. The code is `src/js/one-time-pad.js`; it adds no dependency.
- **Record of use.** The page keeps, per pad and sender, the next key slot and stream offset it sends from, how far it has read, and a stop, in localStorage under `oogaboogaland.pad.<pad id>.<sender>`. Slot and bytes are written as used, under a Web Lock across tabs, before anything is sealed with them. So a failed or refused send never sends new text with them. Retry sends the identical frame while nothing was sealed after it; once a later line has gone, it seals the same text again on a fresh slot and fresh bytes. A reload carries on where the record says. A browser that cannot write the record, keep it, or lock it stops the pad.
- **A pad this browser has no record of.** Loading a file with no record here asks the visitor whether the file has never been used. Only a yes starts it, because a browser that lost its storage would otherwise use the pad again from the start, and if both sides had lost theirs nothing could notice. Storage is lost by clearing site data, in a private window when it closes, by Safari deleting a site's storage after seven days without a visit, or when the browser evicts it under pressure. The page asks the browser to keep this site's storage (`navigator.storage.persist`), which it may refuse. A pad made on this page starts at once.
- **Hellos and acks.** Each side opens with a hello carrying a fresh random nonce and the digest, and answers the other's hello with an ack carrying that nonce and how far it has read the sender's half. Neither uses stream bytes. Each nonce is answered once, and a conversation answers eight hellos at most, so the room playing a hello again spends nothing. A side may speak only after an ack to its latest nonce, and only until the line opens, so an ack the room kept from an earlier conversation, or a true one that comes after, proves nothing. If the other side has read text this device had not sent, this device's record is behind (the pad was used before, on another device, in a browser that lost its storage, or from a restored copy). It stops before saying a word, ends the conversation, and records the stop, so the pad never starts on this device again. Text is the check because its bytes are what must never be used twice; key slots only key a tag, and the other side may have read any this device sealed, in whatever order the room delivered them. A hello the room refused, or one not answered eight seconds after the other side's came, is said again with a fresh nonce, three times at most.
- **Lines that go missing.** "Sent" means the room passed a line on, not that it arrived. A line is shown once: frames already read, and a copy sealed again of a line already shown (a Retry after the room passed the first one on), are dropped. Stream bytes the reader skipped over are a gap: once a later line shows, the reader sees a note that a line hasn't arrived, and a line that fills the gap later shows marked late and takes the note away. So a line the room drops, holds back or reorders is never lost without a word, though the room can still keep it from arriving.
- **The room.** `invite`, `accept`, `decline`, `block`, `end` and `data` (`worker/src/protocol.js`); a `declined` or `withdrawn` sent because the other page left carries `reason: "left"`. The room relays each `data` frame, base64 of at most 724 characters, from one end to the other while both still hold the conversation, at `PM_HZ` a second, and answers `ok` or `refused`; the page drops anything longer unread. `accept`, `decline`, `block` and `end` have a rate of their own (`PM_CONTROL_HZ`), and blocking someone already blocked writes nothing. It keeps who invited whom (at most four out) and who talks to whom in the attachments. Each account's blocks (32 at most) and rate limits stay with it across reconnects while the room is awake, as chat's do. It never keeps, stores or logs a frame. The conversation ends when either side ends it or leaves, and nothing waits for someone offline.
- **What it protects.** The message text, from the room, Cloudflare and the network, as long as the page's code and the pad file are trustworthy. Not who talks to whom, when, or how long each line is. Not a compromised device, a page served with other code, or the other person copying what was said. Not a pad used again where the device that used it has no record of it and the visitor says the file is new. Use a pad on one device, and don't restore a browser profile in the middle of a conversation: a record rolled back that way is caught only when the other side has read the lines it forgot, so if the room also dropped those lines, nothing catches it. No promise of anonymity or guaranteed erasure from memory. The private input turns spellcheck off, so a browser's cloud spellchecker never sees what is typed there.

## The EntropyLab chalkboard

The chalkboard by the lab's mouth is one board for every signed-in player (`src/js/chalk-board.js`, `src/js/chalkboard.js`, `net.js`, `worker/src/room.js`, the `CHALK_*` rules in `worker/src/protocol.js`). Signed out, or with no backend, each visitor keeps their own board in the browser, as before.

- **One writer at a time.** An Ooga standing in front of the board, within 2.4 m of its middle (the Sphere keypad's reach), gets the WRITE prompt; Space, the act button or a tap asks the room to hold the board (`take`). The room grants it only to an Ooga body in the `outside` zone whose last pose stands there (`chalk-board.js` `near`, the same spot the hub checks against where it places the board), and only while nobody else holds it, and tells every page (`chalk-lock`). Anyone else asking is refused with the holder's name; the board's tooltip names them too.
- **Letting go.** Closing the board lets go (`drop`). So does the room, when the holder's pose leaves the board, their zone or body changes, or their socket closes. A holder who has sent nothing for a minute (`CHALK_IDLE_MS`) gives way to the next Ooga to ask; nothing runs on a timer for this. The room forgets who holds the board when it sleeps; the holder's next edit takes it back if it is still free and they still stand there.
- **Edits.** The board is the same list of marks the page always kept: chalk and eraser lines and typed characters, in thousandths of the board on the wire. Every chalk frame a page sends carries the board's layout `v` (`chalk-board.js` `VERSION`, 2 since the board grew half again each way), and the room ignores chalk frames on any other layout. Edits are `line` (a new line from its first points), `more` (points on it), `type` (characters), `back` (backspace, only within the writer's own turn) and `wipe` (clean, or back to the original message). Page and Worker apply them through the one `chalk-board.js` `apply`, so every copy changes the same way. The holder's page batches a line's points a few to a frame, at most every 0.1 s, under the 256-character frame limit. The room relays each edit to every other page as it comes, so the board fills in live in every scene; a page keeps the board current even off the island. An edit over 30 a second (`CHALK_HZ`) is dropped unanswered, and the holder's next edit gets the room's board back instead of being applied; so does an edit that does not apply. A page is sent a corrective board at most once every 2 s (`CHALK_TELL_MS`), so no stream of edit frames makes the room send a full board for each.
- **Limits.** As before: 550 marks and 10,000 points in all (the original message counts), 1,000 points in a line. A line or text stops at the limit, as drawing on a full board did.
- **Storage.** The room keeps the board in its storage (`chalk`): at most one write every 5 s while someone writes (a short timer after an edit, which also keeps the room awake until the last edit is stored), one at once on a wipe, and one when the holder lets go. Never a write for each point, or a recurring save while unchanged. The original board has no storage record: resetting deletes the saved drawing, and the room reconstructs the original on startup. A blank board keeps only `{ marks: [], v: 2 }` so it stays blank after a restart. Repeated clear/reset commands are skipped on both the page and the room, without broadcasting, saving or starting a timer. A drawing stored before the board grew (no `v`) loads in the middle of the bigger board (`widen`: the first board's face is its middle two thirds each way, so every mark keeps its size and place with a new margin round it), and is stored in the new layout at its next save; the page does the same once for a board kept in this browser (`ooga-chalkboard-v2` read into `ooga-chalkboard-v3`). A full board measures about 125 KB as JSON. A new or redeployed room starts with what it stored, or the original message.
- **Mixed versions.** The room advertises `chalk-v2` in `welcome.features`. A page on an older room keeps its own board. A page from before the board grew still shows the room's board, smaller in its smaller board, but the room takes none of its frames.
- **Cost.** One `chalk-board` to each page as it joins (a few KB, up to the full board), and the holder's edits to every page, about ten small frames a second while someone draws, none otherwise. Pages repaint the board's texture at most ten times a second while edits arrive, as they did while drawing locally. Untested: real two-account play on staging, phones, and Durable Object storage and request usage, which need a deploy.

## DSB Land's free hardware wallets

The vending machine's exploding parody wallets (`src/js/wallet-bombs.js`, `worker/src/room.js`, the `WALLET_*` rules in `worker/src/protocol.js`) are shared between signed-in players in the same zone. Signed out, each page has its own, as before.

- **Each page runs its own.** The page sends what happens to its own visitor's devices: `take` (with its look), `down` where it lands, `up`, `throw` from where and how fast, and `blast` (the devices that went off together). Every event carries the owner's seconds left, which the room turns into an end time on its own clock, so every page counts the fuse down together. Nothing is hit or kept; drawing only.
- **Others' are mirrors.** Another player's device is drawn from those events: carried over their head, set down, or flying on from the throw by its age, with its name and seconds as one's own. A mirror cannot be picked up. Mirrors take at most 9 of the page's 16 device slots (`MIRROR_CAP`), so the 7 the visitor's own can need at once (one every 3 s for a 21 s fuse) are always free, however many play nearby; a mirror past that is not drawn. A blast heard from its owner sets it off with the flash, fireball, scorch and knock-back of one's own, and it chains into the devices on this page, which then report their own blast. A mirror whose blast never comes (its owner left, or their tab stopped) goes off 1.5 s past its end; one carried by nobody in sight just goes.
- **The room.** It relays each event at once to the pages in the zone where the device is (its carrier's zone while carried), never back to the sender, from an Ooga in a DSB zone only, 8 a second with a burst of 8. It keeps each player's live devices, 8 at most and each a little past its end, and hands those in a zone to a page walking into it. A carried device walking into another zone is announced there. These live in memory only: a room that sleeps forgets them, and they end within 21 s anyway.
- **Mixed versions.** An older Worker ignores the messages and pages keep their own devices. An older page ignores what it is sent.
- **Cost.** A few small frames per device: taking, setting down or throwing it, and its blast, to the players in one zone; nothing each frame. Untested: two signed-in players on staging, phones, and Durable Object usage.

## Banning

A ban refuses the next sign-in and the next room connection. The existing once-a-minute room alarm also checks each connected account in D1 and kicks a banned or deleted account with `revoked`; active chat, presence and room voice eligibility end at the next successful sweep (normally within a minute). A failed D1 read leaves that account connected and retries on the next sweep, so an outage can extend that interval. The check uses the existing operator D1 ban below: no player-facing moderation endpoint or new permission system. It adds at most one player read per connected account per sweep and no new timer.

This is account-level revocation, not per-session revocation: deleting session rows alone (including signing out all sessions) refuses subsequent HTTP requests and reconnects but does not end another already-open socket. An already-established SFU connection is not forcibly closed by the ban check; the room drops the player and removes its voice eligibility from peers, whose clients stop receiving it. Revoking SFU credentials or immediately terminating media independently of cooperating clients would need a separate service-supported design.

```sh
cd worker
npx wrangler d1 execute oogaboogaland --remote --command \
  "UPDATE players SET banned_at = unixepoch(), ban_reason = 'reason' WHERE login = 'someone'; DELETE FROM sessions WHERE player_id IN (SELECT id FROM players WHERE login = 'someone');"
```
